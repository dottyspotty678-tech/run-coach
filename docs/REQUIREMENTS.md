# Run Coach — redesign requirements (v1)

Status: definitive specification for the v1 redesign. The UI designer and backend developer
implement exactly what this document says. Where this document is silent, prefer the simplest
behaviour consistent with the product vision. Anything in section 7 (Roadmap) is explicitly
NOT in v1.

Deployed app: https://run-coach-fawn.vercel.app
Stack (unchanged): Next.js App Router + TypeScript + Tailwind v4 on Vercel; Supabase Postgres;
Strava OAuth; Microsoft Graph OAuth; Anthropic Claude API; Vercel Cron. Single user. Installed
as an iPhone PWA (Add to Home Screen).

---

## 1. Product vision

Run Coach turns a chaotic consultant's travel calendar and a patchy Strava history into one
clear answer, instantly on opening: **what should I do tonight — which run, and what am I
eating?** It plans the week every Sunday around real free time and real travel, and it keeps
food simple, varied and low-waste without ever counting a calorie.

## 2. The user and their week

You are a UK-based management consultant. A typical fortnight: Preston Monday to Thursday,
London Friday to Sunday, then a weekend in the Lake District. Free time is evenings after
work (often in a hotel, sometimes after client dinners) and parts of the weekend. You run
seriously when a race is on the horizon — recent 28-day volume is around 200 km — but travel
breaks the rhythm and week-long gaps happen.

How the app fits the week:

- **Sunday evening (the planning ritual, ~10 minutes).** The weekly plan has already been
  generated by the 18:00 cron. You open the app, read the week ahead against your calendar,
  regenerate if the calendar has changed, and skim the shopping list before the weekly shop.
- **Weekday evenings (the glance, ~20 seconds).** You open the app in a hotel corridor or on
  the sofa. The first screen answers, without a single tap: what is today's session, is today
  a travel day, and what is dinner. Then you close the app.
- **Ad hoc.** Occasionally you check recent activities after a run, tweak a setting, or fix a
  broken Strava/Microsoft connection when a banner tells you to.

Everything in this document is judged against those three moments. If a feature does not make
the Sunday ritual or the evening glance better, it does not belong in v1.

## 3. v1 feature specification

### 3.0 Navigation structure (Must)

Bottom tab bar, always visible, five tabs in this order:

1. **Today** — the home screen and PWA start URL (`/`).
2. **Plan** — the week's training plan plus a calendar context strip.
3. **Food** — the week's meal plan and the shopping list.
4. **Activity** — recent Strava activities and simple volume stats.
5. **Settings** — race goal, preferences, connections, sync.

Rules:

- One tap from anywhere to any tab. No hamburger menu. No horizontal-swipe-only navigation.
- The full calendar event list is a secondary screen (reachable from the Plan screen's
  calendar strip and from Settings → Connections). It is deliberately buried: the calendar is
  an input, not a destination.
- The active tab is visually obvious. Tapping the active tab scrolls its screen to the top.
- Back behaviour: secondary screens (calendar list, PIN screen) show a back affordance in the
  header; tab screens do not.

### 3.1 PIN gate (Must — hard constraint)

Why: the app is on a public URL with no auth. The synced calendar reveals where you are and
will be (client cities, hotels, home weekends). That must not be publicly readable, but a
personal single-user app cannot afford login friction. A 4-digit PIN, remembered per device,
is the deliberate trade-off.

Behaviour:

- The PIN is stored only in the env var `APP_PIN` (4 digits). It never appears in the repo,
  in client-side code, or in the database.
- On first visit from a device (or after cookie expiry), every route renders the PIN screen
  instead: the app name, four dot placeholders, and a large numeric keypad (0–9 and delete —
  do not rely on the system keyboard). Entering the fourth digit submits automatically; no
  submit button.
- Correct PIN: the server sets a cookie and redirects to the originally requested path. The
  cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, max-age 180 days, and its value is an HMAC
  of the PIN using a second env var `APP_PIN_SECRET` (so the cookie neither contains the PIN
  nor is forgeable). Changing `APP_PIN` invalidates all devices.
- Wrong PIN: dots shake, clear, and a neutral message appears ("Wrong PIN — try again").
  After 5 consecutive failures from a session, enforce a 30-second wait before the next
  attempt (server-side; the screen shows a countdown). No hints, no recovery flow — recovery
  is "the owner edits the env var".
- Coverage: Next.js middleware enforces the check on **every page and every API route**, with
  exactly these exemptions:
  - `/api/cron/*` — authenticated instead by the existing `CRON_SECRET` bearer/header check.
  - `/api/strava/callback` and `/api/microsoft/callback` — OAuth redirect targets.
  - Static assets required pre-auth: `/manifest.json`, `/sw.js`, icons, and Next static files.
  - The PIN screen and its verification endpoint themselves.
- The service worker must never serve cached app content to an unauthenticated request; the
  PIN screen route is excluded from runtime caching (see 5.2).
- Verification requirement for the stress tester: with no cookie, every non-exempt page and
  API route returns the PIN screen or 401 respectively — including `/api/plan/generate`,
  sync endpoints, and any data-returning route.

### 3.2 Today screen (Must — the killer screen)

Why: the 20-second evening glance. It must answer "what should I do tonight?" with zero taps.

Content, top to bottom:

1. **Header**: today's date ("Tue 25 Aug") and a context chip when relevant: "Travel day"
   (from the calendar heuristic) or "Race week", plus days-to-race when a race is set within
   12 weeks (e.g. "6 weeks to Manchester Half").
2. **Today's session card** (the hero, largest element): session type as a bold label (Rest /
   Easy run / Intervals / Tempo / Long run / Cross-training), headline (e.g. "45 min easy —
   keep it conversational"), the detail text, and a one-line "why" (e.g. "Recovery between
   Tuesday's intervals and Saturday's long run"). Pulled from the structured weekly plan
   (see 3.3). Rest days get a real card too ("Rest — you've earned it; long run Saturday"),
   never an empty space.
3. **Tonight's meal card**: recipe name, prep-time label (e.g. "20 min"), and the first line
   of instructions. Travel-day meals show the "Eating out" variant (see 3.4). Tapping opens
   the Food tab scrolled to today.
4. **This week strip**: seven small day tiles (Mon–Sun), today highlighted, each showing the
   session-type icon/abbreviation and a small travel dot on travel days. Tapping any tile
   opens the Plan tab scrolled to that day. Completed days (a Strava activity exists on that
   date) show a subtle tick.
5. **Snapshot row**: two or three small stats — last-7-days km, last-28-days km, and current
   training phase. No charts on this screen.
6. **Sunday-evening special state**: from Sunday 17:00 onward, if next week's plan exists, a
   banner sits above the session card: "Next week's plan is ready — review it" linking to the
   Plan tab (which from Sunday 17:00 shows the upcoming week; see 3.3 week-boundary rule).

States:

- **No plan for the current week**: the session and meal cards are replaced by a single card:
  "No plan yet for this week" with a primary "Generate this week's plan" button (invokes
  generation, shows the in-progress state from 3.7).
- **Stale data**: if the last successful sync is older than 24 hours, show a slim banner
  "Data last synced {relative time} — pull down to refresh". Pull-to-refresh on this screen
  triggers the combined manual sync (3.8).
- **Disconnected integration**: a persistent warning banner "Strava disconnected — reconnect
  in Settings" (likewise Microsoft), linking straight to Settings → Connections. Shown when
  a token refresh has failed or no token exists.
- **Offline**: render the cached version with an "Offline — showing saved data" banner
  (see 5.2).

### 3.3 Weekly plan — training (Must)

Why: the Sunday ritual's core artefact, and the source of the Today screen's hero card.

Structural change (required): the plan generation must return **structured per-day training
entries**, not one narrative blob. New shape per day (7 entries, Monday-first):

- `date` (YYYY-MM-DD)
- `session_type`: one of `rest | easy | tempo | intervals | long | cross | race`
- `title`: short headline, ≤ 60 chars ("6 × 800 m at 5k effort")
- `detail`: 1–3 sentences of instruction, including duration or distance
- `duration_min`: integer estimate (0 for rest)
- `why`: one sentence linking the session to phase, calendar or recovery
- `is_travel_day`: boolean echoed from the calendar input

Store this as `training_plan_json` on `weekly_plans` alongside a short `week_summary` string
(2–3 sentences: intent of the week, target weekly km, phase). Keep the existing
`training_plan_text` column populated (a plain-text render of the same content) so nothing
that reads it breaks; new UI reads only the structured form.

Generation logic requirements (the prompt must instruct Claude accordingly):

- Sessions land on realistic days: hard/long sessions on non-travel days where possible;
  travel days get rest, easy runs, or short hotel-friendly sessions ("30 min easy from the
  hotel — out-and-back, no route needed").
- Phase-appropriate using the existing derived phase (base/build/peak/taper/race_week/
  post_race). Taper and race week visibly reduce load; post_race prescribes recovery.
- Consistency-aware: the 28-day summary must include weekly km for each of the last 4 weeks
  and the gap since the last run (not just a single total), and the plan must ramp sensibly
  after a gap rather than assuming continuity.
- If no race goal is set, plan for general fitness and say so in `week_summary`.

Plan screen layout:

- `week_summary` at the top, with phase and weeks-to-race.
- Seven day cards in order, today highlighted and auto-scrolled into view. Each card:
  weekday + date, session-type badge (colour-coded consistently across the app), title,
  detail, duration, travel indicator, and a tick when a Strava activity exists that day.
- Below the day cards: a **calendar context strip** — for each day, any travel-flagged events
  and evening events (starting 17:00 or later), titles truncated. A "Full calendar" link
  opens the calendar list screen (3.6).
- A "Regenerate" action lives in this screen's header (behaviour in 3.7). Also show
  "Generated {relative time}".
- **Week-boundary rule** (applies to Plan, Food and Today's week strip): the "current week"
  is Monday 00:00 to Sunday 16:59 Europe/London; from Sunday 17:00 the screens switch to the
  upcoming week. This matches the existing `getWeekStart` behaviour and the Sunday-evening
  ritual. On Sunday before 17:00, show the current (ending) week.

States: no plan → same empty state and generate button as Today. Generation failed → keep
showing the previous plan (if any) with an error banner and "Try again" (3.7).

### 3.4 Weekly plan — meals (Must)

Why: decision fatigue is the enemy. One evening meal per day, planned around travel and
training, reusing ingredients. Qualitative only — **no calories, no macros, no gram-level
nutrition anywhere in the app, ever**.

Structural change (required): each of the 7 meal entries gains:

- `meal_type`: `home` (a recipe) | `travel` (eating-out guidance) | `assemble` (≤ 10-minute
  no-cook or one-pan fallback for late/hotel-adjacent evenings)
- `prep_time_min`: integer (0 for `travel`)
- existing fields stay: `date`, `recipe_name`, `ingredients[]`, `short_instructions`

Generation logic requirements:

- Travel-flagged days must be `meal_type: travel`: no recipe, instead 1–2 sentences of
  sensible ordering guidance tied to training and weight goal ("Hotel dinner: grilled fish or
  a chicken salad, skip the chips — tempo session tomorrow"). `ingredients` empty.
- Home days: varied across the week but sharing a deliberately small ingredient pool; the
  prompt must ask for maximum reuse of fresh/perishable ingredients across the week's home
  meals. Respect dietary restrictions and disliked ingredients from settings; scale wording
  to household size.
- Hard-session and long-run days get heartier, carb-forward meals; rest days lighter — stated
  qualitatively ("bigger portion tonight — long run tomorrow"), never numerically.
- Weekend home days may include one batch-cook suggestion whose leftovers cover a named
  weekday.

Food screen layout: seven day cards (same week-boundary rule as 3.3), today highlighted and
auto-scrolled. Each card: weekday + date, `meal_type` badge (Home / Eating out / Quick),
recipe name, prep time, ingredients as a compact list, instructions (collapsed behind a
"Method" disclosure on home meals — the glance needs the name, not the method). A segmented
control or clearly separated section at the top switches between **Meals** and **Shopping
list** (3.5).

### 3.5 Shopping list (Should)

Why: the Sunday shop. The ingredient-reuse promise is only real if the week collapses into
one short list. Judged valuable: include it.

- Generated as part of the same weekly Claude call: a `shopping_list` array of
  `{ item, quantity_note, category }`, consolidated across the week's `home` and `assemble`
  meals only (travel days contribute nothing). `quantity_note` is qualitative
  ("2 large", "1 bag", "small bunch") — no weights unless natural (e.g. "500 g passata").
  `category` is one of: `fruit & veg | meat & fish | dairy | store cupboard | bakery | other`.
  Assume a stocked store cupboard: the prompt should exclude true staples (oil, salt, pepper,
  common dried herbs/spices) from the list.
- Stored in `weekly_plans` (new `shopping_list_json` column).
- UI: grouped by category, each item with a checkbox. Checked state persists **locally on the
  device** (localStorage keyed by `week_start_date`) — it does not sync between devices and
  resets with each new week's plan. Checked items move to the bottom of their group and show
  struck-through. A "Reset ticks" text action clears the week's checks.
- Empty state (all seven days travel): "No shopping needed this week — you're away."
- Regenerating the plan replaces the list and clears the checks.

### 3.6 Activities and calendar views (Should)

**Activity tab** (Should): the training log, for post-run checks and Sunday reflection.

- Top: a simple bar chart of weekly km for the last 8 weeks (current week highlighted), with
  last-7-day and last-28-day totals beside it. No pace charts, no heart-rate analysis — the
  detailed toys live in Strava; this app only needs volume and consistency.
- Below: reverse-chronological activity list (last 30 days, matching sync window). Each row:
  date, activity name, distance km, moving time, average pace min/km. Runs only get the pace;
  other types show distance/time. Tapping a row does nothing in v1 (no detail screen).
- Empty state: "No activities in the last 30 days" plus a Sync now button; if Strava is not
  connected, a Connect Strava card linking to Settings → Connections.

**Calendar list screen** (Should — secondary, not a tab): next 14 days grouped by day; each
event with time (24-hour), title, and a Travel badge where flagged. Purpose: sanity-check
what the planner sees, and spot when the travel heuristic mis-flags something. A short footer
explains the heuristic ("Days are marked as travel when an event mentions travel, flights,
trains or hotels, or spans multiple days"). Empty state mirrors the Activity tab pattern.
No editing — the calendar is read-only.

### 3.7 Plan generation and regeneration (Must)

- **Automatic**: existing Sunday 18:00 (UTC) Vercel cron generates the upcoming week's plan.
  Unchanged, except it now produces the structured formats of 3.3–3.5. The rule is simple:
  the cron always generates the upcoming week's plan, overwriting any manually generated one
  for that week (one scheduled call per week is the budgeted baseline), and it never
  generates for any week other than the upcoming one.
- **Manual generate/regenerate**: available from Today (empty state) and Plan (header).
  Regenerating when a plan exists requires a confirmation sheet: "Replace this week's plan?
  This uses an AI call and clears shopping-list ticks." Confirm / Cancel.
- **In-progress state**: the triggering button shows a spinner and the label "Planning your
  week… (about 30 seconds)". The screen stays usable; the old plan remains visible until the
  new one lands. Disable the trigger while a generation is in flight.
- **Failure**: previous plan is never deleted or overwritten until a new plan is successfully
  stored (generate-then-swap). On failure show: "Couldn't generate the plan — try again in a
  minute." with a Retry action. Log the underlying error server-side.
- **Rate limiting** (cost control, Must): server-enforced — minimum 2 minutes between manual
  generations and a maximum of 8 manual generations per calendar day. Exceeding it returns a
  friendly message ("Easy tiger — you can regenerate again in a moment."). The cron is exempt.
- Generation input must be fresh: a manual generation first runs the combined sync (3.8)
  best-effort — if a sync fails, proceed with cached data and note staleness in the stored
  `input_snapshot_json`.

### 3.8 Sync behaviour (Must)

- **Cron** (existing, keep): daily 06:00 UTC combined sync — Strava last 30 days, Microsoft
  calendar next 14 days, with token refresh. Authenticated by `CRON_SECRET`.
- **Manual**: one combined "Sync now" action (Settings → Connections, plus pull-to-refresh on
  Today). Runs both providers; each reports independently. Never let one provider's failure
  block the other.
- **Status surfacing**: Settings → Connections shows per provider: connected state, last
  successful sync time (relative, e.g. "2 h ago"), and last error if the most recent attempt
  failed. Store `last_synced_at` / `last_error` per provider (new small `sync_status` table
  or columns on `oauth_tokens`).
- **Token failure handling**: when a refresh fails with an auth error, mark the provider
  disconnected (drives the Today banner in 3.2) rather than retry-looping. Reconnecting via
  OAuth clears the state.
- Syncs must remain idempotent upserts (as today). Delete calendar events from the cache that
  no longer appear in the 14-day window fetch, so cancelled trips do not haunt the plan.

### 3.9 Settings (Must)

One screen, three sections, saved via explicit Save buttons per section (auto-save is not
required and risks partial states):

1. **Race goal**: name, distance (preset chips 5k / 10k / Half / Marathon plus a custom km
   field), date (native date picker), optional target time (hh:mm:ss). Below the form, a
   read-only phase card: "Build — 9 weeks to race day", updating on save. A "Clear race"
   action (with confirm) removes the goal; the app then plans for general fitness.
   Validation: race date in the past → warn and show `post_race` phase, do not block saving.
2. **Food preferences**: weight goal (segmented: Lose / Maintain), dietary restrictions and
   disliked ingredients (tag-style input: type, add, tap to remove — replacing free-text
   comma fields), household size (stepper, 1–6).
3. **Connections**: Strava and Microsoft calendar cards, each showing connected state, last
   sync, Connect/Reconnect button, and a combined "Sync now" button with per-provider result
   feedback. Include a Disconnect action per provider (deletes the stored token; confirm
   first).

Footer: app version, and "PIN protected · change the PIN via the server configuration" (no
in-app PIN change in v1).

### 3.10 Design language (Should — direction for the UI designer)

- Mobile-first at 390 px; must remain usable at 320 px. This is a phone app that happens to
  render on desktop, not the reverse.
- Respect the iOS safe areas (notch, home indicator) in standalone PWA mode; the tab bar
  sits above the home indicator.
- Light and dark mode following the system; dark mode matters (evening use).
- Typography-led, card-based, generous tap targets (≥ 44 px). One accent colour used for
  primary actions and the active tab; a fixed colour per session type used consistently
  (badges, week-strip tiles, chart). No gradients or decorative illustration.
- Every screen has designed empty, loading (skeleton, not spinner-only page), error and
  offline states as specified above. The stress tester will check each.

## 4. Content and tone

- **UK English everywhere** in app copy and generated content: -ise endings, "sport",
  kilometres, 24-hour clock, DD MMM date style. The generation prompt must explicitly demand
  UK English and metric units (km, min/km).
- Training copy: concise, practical, coach-like — direct instructions with one line of
  rationale. Encouraging but never gushing; no exclamation marks in generated plans; no
  emoji anywhere. Reads like a good club coach texting you, not a fitness influencer.
- Meal copy: recipe names are plain and appetising ("Chorizo and butter bean stew"), methods
  ≤ 4 short steps, written for a tired person at 20:30. Eating-out guidance is suggestive,
  never preachy ("skip the chips" is fine; moralising about food is not).
- Absolute content bans (enforced in the prompt and checked by the stress tester): no
  calorie, kilojoule, macro, or "points" numbers; no body-weight targets; no medical claims.
- App chrome copy is sentence case, short, and human: "Sync now", "Plan your week",
  "Couldn't reach Strava".

## 5. Non-functional requirements

### 5.1 Performance

- Today screen interactive in under 2 seconds on 4G on an iPhone; skeleton visible under
  500 ms. Server-render the data views; avoid client-side data-fetch waterfalls.
- No layout shift as data loads (skeletons reserve space).
- Payload discipline: no heavy chart libraries for one bar chart (hand-rolled SVG or a tiny
  dependency); no fonts beyond one variable font or the system stack.

### 5.2 Offline and PWA

- Installed-PWA behaviour is first-class: standalone display, correct icons, themed status
  bar, app opens on Today.
- Offline expectation is **read-only recency**: the service worker caches the app shell and
  the most recently viewed data screens (network-first with cache fallback for navigations),
  so on a train with no signal the last-seen plan, meals and shopping list still render, each
  with the offline banner. Writes (sync, regenerate, settings, shopping ticks excepted —
  ticks are localStorage and work offline) fail gracefully with a clear message when offline.
- The PIN verification endpoint and PIN screen are never cache-served in a way that bypasses
  the gate (see 3.1); cached pages are only ever served to a browser that obtained them, which
  the cookie gate already implies.

### 5.3 Privacy and security

- The PIN gate exists because `calendar_events` is effectively a public itinerary of your
  whereabouts (client cities, hotels, family weekends) if unprotected — plus meal/weight-goal
  preferences and OAuth-linked data. Nothing readable without the cookie; verified per 3.1.
- Secrets (`APP_PIN`, `APP_PIN_SECRET`, `CRON_SECRET`, OAuth client secrets, Anthropic and
  Supabase keys) live only in Vercel env vars. The Supabase service key is server-only; no
  Supabase access from the client.
- Do not log calendar event titles or generated plans in server logs beyond error context.

### 5.4 Cost awareness

- Baseline Claude usage: 1 scheduled call/week + occasional manual regenerations, enforced by
  the 3.7 rate limits. One generation call produces training, meals and shopping list
  together — never split into multiple calls.
- Cron cadence stays daily/weekly as-is. No polling, no background refresh loops, no
  speculative generation.

### 5.5 Reliability and time

- All user-facing dates, the week boundary, and "today" logic use **Europe/London**
  explicitly (the current code uses server-local time — Vercel is UTC — so today/week
  boundaries can be off by an hour around midnight; fix this in the redesign).
- Cron schedules remain in UTC (06:00 and Sunday 18:00 UTC); the ±1 hour BST drift on the
  cron firing time is acceptable and does not need solving in v1.
- A failed cron run must not corrupt state (generate-then-swap per 3.7; idempotent syncs
  per 3.8).

## 6. Data model changes summary (for the backend developer)

- `weekly_plans`: add `training_plan_json` (jsonb), `week_summary` (text),
  `shopping_list_json` (jsonb); keep existing columns; extend `meal_plan_json` entries with
  `meal_type` and `prep_time_min`.
- Sync status: add `last_synced_at`, `last_error` per provider (columns on `oauth_tokens` or
  a small `sync_status` table — developer's choice, surfaced per 3.8).
- Supabase RLS note: the current policies check `auth.role() = 'authenticated'` but the app
  uses only the service key and there is no Supabase Auth user — access control now lives
  entirely in the PIN middleware. Keep RLS enabled with service-role access; do not add
  Supabase Auth.
- No other schema changes. No new third-party services, packages requiring accounts, or API
  signups in v1.

## 7. Out of scope for v1 / roadmap

Each deferred because it needs a new integration, new data, or is polish on top of an
unproven core — v1 must ship on existing integrations only.

- **Weather-aware planning** (rain/heat shifts sessions and kit advice): needs a weather API
  signup.
- **Voice briefing** ("read me tonight's plan" via ElevenLabs): new paid service; the glance
  screen covers the need for now.
- **Training-science knowledge library** (curated article summaries grounding the plans): the
  prompt's composable-context design already leaves a slot; curation is a content project,
  not a build task.
- **Push notifications** (Sunday "plan is ready", morning session nudge): iOS PWA push is
  possible but fiddly; validate the pull habit first.
- **Route suggestions in client cities** (hotel-door 5k loops): needs a mapping/routes API.
- **Strava webhooks for instant activity sync**: daily cron + manual sync is adequate; webhook
  adds infrastructure for marginal freshness.
- **Plan feedback loop** ("too hard / too easy" adjusting next week's generation): valuable,
  but needs a season of real usage data to design well.
- **Recipe memory and favourites** ("more like this, never that again"): start capturing
  signal only after the meal plans prove themselves.
- **Multi-race season planning** (A/B races, tune-up events): single goal race keeps v1 logic
  auditable.
- **Kit/packing prompts for travel weeks**: cute, not core.
- **In-app PIN change and multiple PINs**: env-var change is fine for one user.
